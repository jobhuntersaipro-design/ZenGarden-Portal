# Storefront revamp — plan index

Written 2026-09-10 from the approved storefront canvas:
https://claude.ai/code/artifact/52adbe2d-50aa-441c-b00b-2dc76be12c18
(sources in `docs/design/storefront/`; `Shop.dc.html` is the working prototype
and wins over the static artboards where they differ). This folder holds one
implementation plan per phase. Coders read `docs/specs/00-master.md`, then this
file, then their phase file — and nothing else unless the phase file points to
it.

Precedence is the master spec's: the canvas wins for visuals, the master wins
for data model and architecture, the phase file wins for behaviour and
acceptance criteria.

## What this builds on

Phase 16 shipped a sign-in-only shop at real paths under `/shop`, rewritten
from the shop host by `src/proxy.ts`: a catalogue, a product page, a cart that
is the client's `DRAFT` `WebOrder` and never stores a price, `submitWebOrder`,
the ops review screen at `/web-orders/[id]`, and a client order list. Every one
of those survives; this revamp reshapes the screens around them and adds what
the customer drew afterwards.

## Decisions taken 2026-09-10

| Question | Decision |
|---|---|
| Phase split | Six phases, 17–22, in the order below. Each is one branch, one PR, independently shippable, one history entry in `context/current-feature.md`. |
| Guest access | **Public, as drawn.** Home, catalogue, product pages and the cart need no account; every trade price is visible to anyone who finds the shop host. Sign-in happens at checkout and nowhere earlier. This reverses Phase 16 §11 ("sign-in-only end to end") deliberately. |
| Request an account | `AccessRequest` gains a `CLIENT` kind with company and phone. Approving a customer request in `/admin` means picking an existing buyer or creating one from the company name, then running the existing client invite (temporary password, link to the shop host). |
| PDF renderer | `@react-pdf/renderer`, server-side, at the moment the order is sent. A faithful redraw of the A4 artboard in its own primitives, not a screenshot. |

## Assumptions made without asking

These were not on the canvas and did not change the shape of the work, so they
are stated here rather than asked. Any of them is a one-line change if wrong.

- **Supplier details** (the bracketed `[YOUR …]` text on the footer and the
  purchase order) come from environment variables — `SUPPLIER_NAME`,
  `SUPPLIER_EMAIL`, `SUPPLIER_PHONE`, `SUPPLIER_ADDRESS`,
  `SUPPLIER_REGISTRATION_NO`, `SUPPLIER_TAX_LABEL`, `SUPPLIER_TAX_RATE` — all
  optional; an unset one omits its row. A settings table editable by a super
  admin is the better long-term home and is a phase of its own if asked for.
- **Account-menu rows without a drawn destination.** *Delivery updates* opens
  `/orders?filter=open`. *Talk to our team* is a `mailto:` to `SUPPLIER_EMAIL`
  (the external-link glyph on the canvas says it leaves the site). *Help* is
  dropped — nothing on the canvas says what it opens, and a row that goes
  nowhere is worse than no row.
- **Catalogue filter facets** are Brand, Pack size and Market. The static
  artboard also draws Size and Price: `Product` has no size column (the size is
  a substring of the name) and a price range on a 300-product catalogue was not
  worth a control. Both are out of scope, named in Phase 17.
- **"Bottles" reads "pieces".** The prototype says "18 bottles"; the catalogue
  holds caps, sachets and inserts too, and `src/lib/cartons.ts` already says
  pieces. Same for the per-piece price line on the product page.
- **The client's Purchase orders list** carries every purchase order of the
  buyer that has a document — the ones generated by the shop *and* the ones ops
  keyed from an emailed PDF, which is the buyer's own document. The canvas copy
  mentions only generated ones; leaving the scanned ones out would make the
  list disagree with *Your orders*.
- **Tax on the generated purchase order** prints only when `SUPPLIER_TAX_LABEL`
  and `SUPPLIER_TAX_RATE` are set; otherwise the row is omitted and the total
  equals the subtotal. Ops can still enter tax at confirm, as today.

## Conventions every phase follows

- **Two link rules, one module.** Every `<Link>` in storefront code is
  browser-relative and every `revalidatePath` names the real `/shop/…` path,
  both through `src/lib/shop-routes.ts`. Each phase adds its routes there and
  nowhere else.
- **Reads for a client are explicit narrow selects.** Never `include`. The
  reasons are in `src/lib/queries/web-orders.ts` and they have not changed:
  `PurchaseOrder.notes`, `PoStageEvent.note` and the ops team's names and
  pictures must not reach the shop. Every new client-facing query gets a test
  asserting its projection by equality.
- **Guests read only what the catalogue shows.** Any Server Action callable
  without a session reads `SHOP_VISIBLE` products and nothing else, takes
  bounded input, and writes nothing.
- **Tokens only.** No raw hex, px or arbitrary Tailwind value. The prototype's
  inline palette maps 1:1 onto `@theme`; `docs/design/storefront/_parts.md`
  is the lookup. The one new token each phase may add is named in its file.
- **Dark pills.** The master spec says one `button-primary` per screen. A
  catalogue grid has one per card by design — the card's Add to cart is the
  product's own primary action — and that is the single deliberate exception,
  recorded in Phase 17. Everywhere else the rule holds.
- **Verification is a real journey with numbers.** Each phase ends with the
  checks its file lists: `npm run test`, `npx tsc --noEmit`, `npm run lint`,
  `npm run build`; the routes at 390, 768 and 1440px with zero horizontal
  overflow; HTTP statuses read from the wire, row counts before and after,
  and every piece of test data removed. A claim without a measurement is not a
  report.
- **History.** On merge, `context/current-feature.md` gets the entry — what was
  built, what the browser found that the build could not, what was not
  verified and why.
